# API Development

## What is an API?

An **API** (Application Programming Interface) is a contract between a client and a server. The client makes a request in a specific format, and the server returns a response in a specific format. Both sides agree on this contract.

Think of an API like a restaurant menu. The menu tells you what you can order (the endpoints), how to order it (the request format), and what you will get (the response format). You do not need to know how the kitchen works. You just follow the menu.

## REST API Design

**REST** (Representational State Transfer) is the most common style for web APIs. The key principles:

- **Resources as nouns** - URLs represent resources: `/products`, `/orders`, `/users`
- **HTTP methods as verbs** - GET reads, POST creates, PUT updates, DELETE removes
- **Proper status codes** - 200 for success, 400 for bad request, 404 for not found
- **JSON format** - Request and response bodies use JSON

## API Versioning

APIs change over time. You add new fields, change response formats, or remove old endpoints. **Versioning** lets you make changes without breaking existing clients:

```
/api/v1/products
/api/v2/products
```

The simplest approach is URL-based versioning. Put the version in the URL path:

```go
mux.HandleFunc("GET /api/v1/products", v1.ListProducts)
mux.HandleFunc("GET /api/v2/products", v2.ListProducts)
```

Other approaches include header-based versioning (`Accept: application/vnd.myapi.v2+json`) and query parameter versioning (`?version=2`). URL-based is the most common and easiest to understand.

## Request and Response Format

Always use **JSON** for request and response bodies. Define clear structs:

```go
// Request
type CreateProductRequest struct {
    Name        string  `json:"name" validate:"required"`
    Description string  `json:"description"`
    Price       float64 `json:"price" validate:"required,gt=0"`
    Stock       int     `json:"stock" validate:"gte=0"`
    Category    string  `json:"category"`
}

// Response
type ProductResponse struct {
    ID          int64   `json:"id"`
    Name        string  `json:"name"`
    Description string  `json:"description"`
    Price       float64 `json:"price"`
    Stock       int     `json:"stock"`
    Category    string  `json:"category"`
    CreatedAt   string  `json:"created_at"`
}
```

Notice that the request and response types are different. The request does not have an ID or CreatedAt because those are generated by the server. The response does not include internal fields like PasswordHash.

## Error Responses

Errors should be consistent and informative. Define a standard error format:

```go
type APIError struct {
    Code    string `json:"code"`
    Message string `json:"message"`
    Detail  string `json:"detail,omitempty"`
}

func respondError(w http.ResponseWriter, status int, code, message string) {
    w.Header().Set("Content-Type", "application/json")
    w.WriteHeader(status)
    json.NewEncoder(w).Encode(APIError{
        Code:    code,
        Message: message,
    })
}

// Usage
respondError(w, http.StatusNotFound, "PRODUCT_NOT_FOUND", "Product with ID 123 does not exist")
respondError(w, http.StatusBadRequest, "VALIDATION_ERROR", "Price must be greater than 0")
respondError(w, http.StatusUnauthorized, "UNAUTHORIZED", "Invalid or missing authentication token")
```

Common error codes:

| Status | Code | Meaning |
|--------|------|---------|
| 400 | VALIDATION_ERROR | Invalid request data |
| 401 | UNAUTHORIZED | Not authenticated |
| 403 | FORBIDDEN | Not authorized for this action |
| 404 | NOT_FOUND | Resource does not exist |
| 409 | CONFLICT | Resource already exists |
| 422 | UNPROCESSABLE | Validation failed |
| 500 | INTERNAL_ERROR | Server error |

## Pagination in API Responses

Every list endpoint should support pagination:

```go
type PagedResponse struct {
    Data       interface{}    `json:"data"`
    Pagination PaginationMeta `json:"pagination"`
}

func (h *ProductHandler) List(w http.ResponseWriter, r *http.Request) {
    page, _ := strconv.Atoi(r.URL.Query().Get("page"))
    limit, _ := strconv.Atoi(r.URL.Query().Get("limit"))

    products, total, err := h.repo.FindPaginated(page, limit)
    if err != nil {
        respondError(w, 500, "INTERNAL_ERROR", "Failed to fetch products")
        return
    }

    pg := pagination.NewResponse(pagination.NewRequest(page, limit), total)

    respondJSON(w, 200, PagedResponse{
        Data:       products,
        Pagination: pg,
    })
}
```

## Rate Limiting

**Rate limiting** prevents clients from overwhelming your API with too many requests. A simple implementation using a token bucket:

```go
type RateLimiter struct {
    visitors map[string]*Visitor
    mu       sync.Mutex
}

type Visitor struct {
    tokens    int
    lastCheck time.Time
}

func (rl *RateLimiter) Allow(ip string) bool {
    rl.mu.Lock()
    defer rl.mu.Unlock()

    v, exists := rl.visitors[ip]
    if !exists {
        rl.visitors[ip] = &Visitor{tokens: 100, lastCheck: time.Now()}
        return true
    }

    // Replenish tokens (1 token per second, max 100)
    elapsed := time.Since(v.lastCheck)
    v.tokens += int(elapsed.Seconds())
    if v.tokens > 100 {
        v.tokens = 100
    }
    v.lastCheck = time.Now()

    if v.tokens <= 0 {
        return false
    }

    v.tokens--
    return true
}

// Middleware
func RateLimitMiddleware(limiter *RateLimiter) func(http.Handler) http.Handler {
    return func(next http.Handler) http.Handler {
        return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
            ip := r.RemoteAddr
            if !limiter.Allow(ip) {
                respondError(w, 429, "RATE_LIMITED", "Too many requests")
                return
            }
            next.ServeHTTP(w, r)
        })
    }
}
```

## API Documentation

Good APIs are documented. The standard for API documentation is **OpenAPI** (formerly Swagger). It describes your endpoints, request formats, response formats, and error codes in a machine-readable format.

There are Go packages that generate OpenAPI docs from your code, like **swaggo/swag**. But even without tools, keep your API documented. A simple README with endpoint descriptions is better than nothing.

## Well-Designed REST API Example

Here is a complete, well-designed API structure:

```go
func main() {
    // Dependencies
    db := connectDB()
    productRepo := postgres.NewProductRepo(db)
    productService := productservice.New(productRepo)
    productHandler := handler.NewProductHandler(productService)

    // Router with versioning
    mux := http.NewServeMux()

    // v1 endpoints
    mux.HandleFunc("GET /api/v1/products", productHandler.List)
    mux.HandleFunc("POST /api/v1/products", productHandler.Create)
    mux.HandleFunc("GET /api/v1/products/{id}", productHandler.Get)
    mux.HandleFunc("PUT /api/v1/products/{id}", productHandler.Update)
    mux.HandleFunc("DELETE /api/v1/products/{id}", productHandler.Delete)

    // Middleware
    var handler http.Handler = mux
    handler = middleware.Logging(handler)
    handler = middleware.CORS(handler)
    handler = middleware.RateLimit(rateLimiter)(handler)

    log.Println("API server running on :8080")
    http.ListenAndServe(":8080", handler)
}
```

The API follows consistent patterns: JSON input/output, proper status codes, pagination, error codes, and versioning. Any developer who understands REST can use this API without reading your code.
